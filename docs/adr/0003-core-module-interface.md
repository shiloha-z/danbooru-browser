# Core module interface: Browser facade with a stateless session

The core module — the single test seam — exposes a `Browser` facade: `next_output(state) -> (Output, state)` is the executor's only entry point (a total function covering restore, cursor advance, page fetch, failure skip, prompt derivation, cache, and state write-back), while panel interactions go through a `Session` handle returned by `restore(state)`, following a stateless restore/action/serialize cycle. Site differences sit behind a `Site` port carrying a `SiteCapabilities` table, so neither core nor UI branches on site identity. The session blob travels with every call and stays the caller's property, keeping ADR-0002's "workflow JSON is the truth" intact; credentials never cross the seam and cache stays an internal implementation.

Three interface designs were produced in parallel and compared on depth, locality, and seam placement. A single `act(session, action)` entry with a string verb table was rejected: maximal depth, but stringly-typed verbs trade away Python's type safety for an interface that is not much smaller. A `Session` aggregate with ~14 methods and sessions held in route memory was rejected: fine-grained verbs, but server-side session state diverges from the workflow-JSON truth and forces frontend reconciliation on refresh and reopen. The adopted shape is the third design — one-function executor path, explicit-method panel handle — extended with the aggregate design's capability table.

Consequences: the interface is the test surface (pytest crosses `Browser`/`Session` with a fake `Site` adapter); the executor adapter is a single call; each route is three steps; failure conditions (`FAILED`/`ANIMATED`/`EMPTY`) are data, while transport and state errors are exceptions.
